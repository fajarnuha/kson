# kson compared with kotlinx.serialization, Moshi, Gson, and Jackson

> **Status: draft.** Every number and behavior claim below comes from code in [`docs/benchmarks`](benchmarks) that was
> run for this document, unless it's marked *(docs)*. Those rows restate the other libraries' own documentation
> and were not re-tested here. Raw output is in [`docs/benchmarks/results`](benchmarks/results).

This draft compares kson's typed path (a `@Kson` interface, with the codec generated by `kson-ksp`) with the four
JSON libraries Kotlin projects most often use. It covers usability, stability, performance, and memory.
It ends with the improvements to kson that the measurements point to.

## Summary

- **Decode speed is on par.** kson decodes a 489 KB page in 1.94 ms. kotlinx.serialization takes 1.73 ms, Moshi
  1.97 ms, Gson 1.82 ms, and Jackson 2.15 ms. On small payloads kson, kotlinx.serialization, Moshi, and Gson are
  within 10% of each other, and Jackson is 25–40% slower.
- **Encoding is kson's weak spot.** It is 2.6× slower than kotlinx.serialization and allocates 4.5× as much,
  because it builds a `JsonObject` tree before writing any text.
- **kson creates about 2.3× the garbage of kotlinx.serialization, Moshi, and Gson on decode**, level with Jackson.
  The cause is the intermediate `JsonValue` tree, and `JsonNumber` in particular. The decoded result itself is the
  smallest of the five.
- **Small runtime and fast cold start.** The runtime is one 279 KB jar with no dependencies, and the first decode
  takes 14 ms (Jackson: 240 ms, 5.6 MB). Its generated code is the largest, because nested codecs are copied into
  every root.
- **Strict and predictable input handling.** kson rejects every malformed input tested, enforces Kotlin nullability,
  caps nesting depth (kotlinx.serialization overflows the stack), and keeps number literals exact. Gson, by
  contrast, puts `null` into non-null properties.
- **Three problems found:**
  - An unknown enum value throws a raw `IllegalArgumentException` that escapes the Ktor converter.
  - The same JSON decoded through two different `@Kson` roots gives objects that aren't `==`.
  - Error messages have no JSON path and include part of the payload.
- **Narrow type support.** There is no `Map`, `Set`, custom adapter, polymorphism, recursion, generics, or key
  renaming, and input must be a `String`.

See [Recommendations for kson](#recommendations-for-kson) for the fixes these findings point to.

## Usability

### Declaring a model

```kotlin
// kson
@Kson
interface User {
    val id: Long
    val name: String
    val nickname: String?                        // optional: missing or null -> null
    val tags: List<String> get() = emptyList()   // default: a getter
    val address: Address

    interface Address { val city: String }
}

// kotlinx.serialization
@Serializable
data class User(
    val id: Long,
    val name: String,
    val nickname: String? = null,
    val tags: List<String> = emptyList(),
    val address: Address,
)
@Serializable data class Address(val city: String)

// Moshi: the same data classes with @JsonClass(generateAdapter = true)
// Gson and Jackson: the same data classes, no annotations
```

| Task | kson | kotlinx.serialization | Moshi | Gson | Jackson |
|---|---|---|---|---|---|
| Decode | `UserJson.decode(text)` | `Json.decodeFromString<User>(text)` | `moshi.adapter(User::class.java).fromJson(text)` | `gson.fromJson(text, User::class.java)` | `mapper.readValue<User>(text)` |
| Encode to `String` | `UserJson.encode(user).toJson()` | `Json.encodeToString(user)` | `adapter.toJson(user)` | `gson.toJson(user)` | `mapper.writeValueAsString(user)` |
| Create a value in code | `userKson { id = 1; … }` or your own class that implements `User` | constructor | constructor | constructor | constructor |
| Change one field | rebuild with `userKson { }` (the generated `Impl` is private, so there is no `copy`) | `copy()` | `copy()` | `copy()` | `copy()` |

kson's interface models give nested types autocomplete at every level, and they let defaults read other properties
(`get() = "settings-$id"`). The trade-off is that a value can't be built with a constructor or changed with `copy()`.

kson has three features the others don't ship: a builder DSL for typed values, a JSON Schema generated from each
model, and jq queries and a CLI (`kson model` generates the `@Kson` interface from a sample response). kson's
immutable `JsonValue` tree also compares numbers by value and keeps their original text, as the stability section shows.

### Error messages

A missing field inside a nested object (`"inner": {}`), taken from [behavior.md](benchmarks/results/behavior.md):

| Library | Message |
|---|---|
| kson | `Missing required key "value" in object {}` |
| kotlinx.serialization | `Field 'value' is required for type with serial name 'probe.KotlinxInner', but it was missing at path: $.inner` |
| Moshi | `Required value 'value__' (JSON name 'value') missing at $.inner` |
| Gson | no error; `value` silently becomes `0` |
| Jackson | no error; `value` silently becomes `0` |

kson's messages never give a location inside the document, so in a large response you can't tell which of the
1,000 `address` objects was wrong. They also embed up to 80 characters of the offending object
(`in object {"id":1,"score":1.5,…}`), which puts response data in logs. kotlinx.serialization does the same with its
`JSON input:` excerpt. Jackson redacts the source by default, and Moshi and Gson print only the path.

## Stability

The full matrix of 34 decode cases, 4 encode cases, and a nesting-depth test is in
[`results/behavior.md`](benchmarks/results/behavior.md). It is produced by
[`BehaviorMatrix.kt`](benchmarks/src/main/kotlin/bench/BehaviorMatrix.kt). As a baseline, all five libraries decode
and re-encode the 1,000-user page to the same JSON values.

### Data binding

| Input | kson | kotlinx.serialization | Moshi | Gson | Jackson |
|---|---|---|---|---|---|
| Required field missing | error | error | error | **`null` in a non-null property** | error |
| `null` for a non-null field | error | error | error | **`null` in a non-null property** | error |
| Missing key with a default | default | default | default | **`null`**: defaults ignored | default |
| `null` for a non-null field with a default | **default** | error | error | `null` | error |
| Unknown key | ignored | **error** | ignored | ignored | **error** |
| Missing nested primitive | error | error | error | **`0`** | **`0`** |
| Top-level `null` | error | error | returns `null` | returns `null` | returns `null` |
| `"42"` for `Int` / `"1.5"` for `Double` | **error** | coerced | coerced | coerced | coerced |
| `42` for `String` | error | error | coerced to `"42"` | coerced | coerced |
| `1.0` for `Int` | `1` | **error** | `1` | `1` | `1` |
| `1.5` for `Int` | error | error | error | error | **`1` (truncated)** |
| `1e400` for `Double` | **`Infinity`** | error | error | `Infinity` | `Infinity` |
| Unknown enum constant | **`IllegalArgumentException`** | error | error | **`null`** | error |

Gson is the only library here that breaks Kotlin's null safety. Because it creates objects without calling the
constructor, a non-null `String` property can hold `null` and fail later, far from the parse. kson follows its type
declarations strictly and is the only library that refuses a quoted number (`"42"` for `Int`). It is lenient in two
places: an unknown key is ignored, as in Moshi and Gson, and a JSON `null` for a non-null property that has a default
falls back to the default, where every other library throws.

**Unknown enum constants escape kson's exception type.** The generated decoder calls `enumValueOf`, so a value
the client doesn't know (for example, a role added on the server) throws `java.lang.IllegalArgumentException`
instead of a `JsonException`. [`kson-checks.md`](benchmarks/results/kson-checks.md) shows this reaching Ktor users.
`KsonConverter` wraps `JsonException` in `JsonConvertException` but lets this exception through unwrapped:

| Body | Thrown by `KsonConverter.deserialize` |
|---|---|
| `{"id":1,` | `JsonConvertException` |
| `{"id":1}` (missing key) | `JsonConvertException` |
| `"role":"OWNER"` (unknown enum) | `java.lang.IllegalArgumentException` |

### Syntax

kson's parser rejects every malformed input in the matrix: trailing commas, comments, single quotes, unquoted keys,
`NaN`, leading zeros, bad escapes, raw control characters, trailing garbage, and truncated or empty input. It is the
strictest of the five. It still accepts a leading byte-order mark, which only Gson also accepts. For comparison:

- **Gson** accepts comments, single quotes, unquoted keys, `NaN`, leading zeros, and raw newlines inside strings.
  It returns `null` for empty input.
- **Jackson** decodes `{…} x` without complaint, because `readValue` ignores trailing content by default.
- **kotlinx.serialization** accepts a leading zero (`01`) and raw newlines inside strings.
- **Moshi** accepts raw newlines inside strings.

### Nesting depth

Untyped parse of 100,000 nested arrays on a 1 MB thread stack:

| kson | kotlinx.serialization | Moshi | Gson | Jackson |
|---|---|---|---|---|
| `JsonParseException` at depth 512 | **`StackOverflowError`** | `JsonDataException` at 255 | `JsonSyntaxException` at 255 | `StreamConstraintsException` at 1000 |

kson's configurable `maxDepth` turns hostile input into an ordinary parse error.

### Equality across roots

KSP generates a separate copy of every nested model for each `@Kson` root. `UserJson` and `UserPageJson` each contain
their own `UserImpl`, `User_AddressImpl`, and so on. So the same JSON user decoded through the two roots gives two
objects that are **not equal**, and neither are their `address` values
([`kson-checks.md`](benchmarks/results/kson-checks.md)):

```
UserJson.decode(user) == UserPageJson.decode(page).users[0]   // false
runtime classes: bench.kson.UserJson$UserImpl vs bench.kson.UserPageJson$UserImpl
```

The README says built and decoded values "compare equal by content". That only holds within one root. Any app that
gets `User` from both a detail endpoint and a list endpoint will see `==` fail, and so will `distinct()`,
`StateFlow` deduplication, and Compose's stability checks. kotlinx.serialization's `data class` models don't have
this problem.

## Performance

JMH average time per operation, lower is better. Each row is 2 forks × 5 one-second iterations after 5 warmup
iterations. ± is JMH's 99.9% confidence interval. The input is always a `String`, because kson accepts nothing else.
Payloads are 535 bytes (one user), 9.5 KB (20 users), and 489 KB (1,000 users). Source:
[`Benchmarks.kt`](benchmarks/src/jmh/kotlin/bench/Benchmarks.kt). Raw output:
[`jmh-human.txt`](benchmarks/results/jmh-human.txt), [`jmh-raw.json`](benchmarks/results/jmh-raw.json).

### Decode (`String` → typed model)

| | kson | kotlinx.serialization | Moshi | Gson | Jackson |
|---|---:|---:|---:|---:|---:|
| 1 user | 1.89 ± 0.04 µs | 1.80 ± 0.03 µs | 1.86 ± 0.03 µs | **1.74** ± 0.05 µs | 2.40 ± 0.10 µs |
| 20 users | 35.1 ± 0.6 µs | **33.8** ± 2.7 µs | 36.8 ± 0.2 µs | 35.2 ± 0.6 µs | 42.2 ± 4.5 µs |
| 1,000 users | 1,942 ± 59 µs | **1,725** ± 31 µs | 1,972 ± 33 µs | 1,816 ± 18 µs | 2,150 ± 31 µs |
| 1,000 users vs. fastest | 1.13× | 1.00× | 1.14× | 1.05× | 1.25× |

kson decodes at the same speed as the others. On the small payloads it is within the error bars of kotlinx.serialization
and Moshi. On the 489 KB page it is 13% behind kotlinx.serialization, level with Moshi, and ahead of Jackson.

|---|---:|---:|---:|---:|---:|
| 20 users | 32.5 ± 3.5 µs | **10.9** ± 0.2 µs | 24.3 ± 2.4 µs | 22.7 ± 0.6 µs | 11.6 ± 0.6 µs |

Encoding is kson's slowest operation: 3.0× kotlinx.serialization at 20 users and 2.6× at 1,000.

### Untyped tree parse (`String` → tree)

| | kson `JsonValue` | kotlinx `JsonElement` | Moshi `Map`/`List` | Gson `JsonElement` | Jackson `JsonNode` |
|---|---:|---:|---:|---:|---:|
| 20 users | 21.7 ± 1.6 µs | **20.2** ± 0.9 µs | 47.9 ± 2.7 µs | 32.0 ± 1.6 µs | 29.5 ± 1.1 µs |
| 1,000 users | 1,175 ± 37 µs | **939** ± 6 µs | 2,539 ± 109 µs | 1,532 ± 47 µs | 1,414 ± 144 µs |

kson's parser is the second fastest tree parser, behind kotlinx.serialization and ahead of Jackson and Gson. This
number also explains the typed decode: kson's typed decode *is* this parse followed by a binding pass (see
[Why kson performs this way](#why-kson-performs-this-way)).

### Cold start (first decode in a fresh JVM)

Time for the first `decode` of one user in a new JVM, including class loading and codec creation. 20 forks per library.

| kson | kotlinx.serialization | Moshi | Gson | Jackson |
|---:|---:|---:|---:|---:|
| 14.0 ± 3.1 ms | **9.6** ± 1.2 ms | 15.4 ± 0.6 ms | 18.6 ± 0.4 ms | 239.7 ± 6.9 ms |

On first use, kson is in the same range as Moshi and Gson. kotlinx.serialization is faster, and Jackson is an order

### Library and generated code size

From [`footprint.md`](benchmarks/results/footprint.md). Jar sizes are before R8 and exclude `kotlin-stdlib`.

| | kson | kotlinx.serialization | Moshi | Gson | Jackson |
|---|---:|---:|---:|---:|---:|
| Runtime jars | 279 KB (1 jar) | 682 KB (2 jars) | 511 KB (moshi + okio) | 326 KB | **5,590 KB** (incl. 3 MB `kotlin-reflect`) |
| Bytecode for the benchmark model | 135 KB, 28 classes | 75 KB, 17 classes | 56 KB, 11 classes | 22 KB, 6 classes | 22 KB, 6 classes |

kson's runtime is small and has no dependencies. It still includes the jq engine and the JSON Schema builder, which
typed-only users don't need. Its generated code is the largest here, for two reasons:

1. Each model gets an `Impl`, a `Builder` (with a `KsonProperty` delegate per property), a decoder, and an encoder.
2. Nested codecs are copied into every root. `User`, `Address`, `Geo`, and `Friend` are generated once inside
   `UserJson` and again inside `UserPageJson`; the build output lists `UserJson$UserImpl` and
   `UserPageJson$UserImpl` side by side. The same duplication causes the equality problem in
   [Stability](#equality-across-roots). An app with 30 endpoints that share a `User` type gets 30 copies of it.

## Why kson performs this way

The numbers follow from three design choices, all visible in the source.

**1. Two passes on both paths.** `KsonDecoder.decode(text)` is `decode(Json.parse(text))`: it builds the complete
`JsonValue` tree and then binds it (`Kson.kt:15`). For the 1,000-user page the tree parse takes 1,175 µs of the
1,942 µs total and 6.05 MB of the 8.56 MB allocated, all of which becomes garbage immediately. Encoding runs the same
way in reverse. `UserJson.encode(user)` builds a `JsonObject` tree (a `LinkedHashMap` for each object and a
`JsonNumber` for each number), and only then does `toJson()` write it. kotlinx.serialization and Moshi stream tokens
directly between the text and the object, in both directions, which is why they allocate less than half as much.

**2. `JsonNumber` is expensive.** It stores the literal and computes a second, canonical string eagerly in the
constructor so that `1`, `1.0`, and `1e0` compare equal. Its `double` value is `by lazy`, which allocates a
`SynchronizedLazyImpl` and a lambda for every number. JOL breakdown for 123 numbers in the 20-user tree
([`retained.md`](benchmarks/results/retained.md)):

```
       123        24      2952   com.fajarnuha.kson.JsonNumber
       123        16      1968   com.fajarnuha.kson.JsonNumber$$Lambda
       123        24      2952   kotlin.SynchronizedLazyImpl
    (+ 246 String + 246 byte[] for literal and canonical text)
```

Reading the number back is also costly. `JsonValue.long` calls `toLongOrNull()`, which takes substrings of the
canonical form and rebuilds the digits in a `StringBuilder` on every call (`JsonNumber.kt:37`).

**3. The generated decoder goes through a builder.** Each object is decoded into a `Builder` whose properties are
`KsonProperty` delegates. That is one extra object per property, and `Long`, `Double`, and `Boolean` values are boxed
because the delegate stores `Any?`. Only then is the `Impl` constructed. The design makes defaults that read other
properties possible, but a decoder could call the `Impl` constructor directly whenever no default is involved.

The same design explains why the parser alone is fast (a tight loop over the `String` with no token objects) and why
kson has no streaming input: everything starts from a complete `String`. The Ktor and Retrofit converters read the
whole body into a `String` before parsing (`KsonConverter.kt`, `KsonConverterFactory.kt`), so a 489 KB response goes from
bytes to a `String` (933 KB on the heap here) to a tree (5 MB), and the `String` and the tree are alive at the same time.

## Recommendations for kson

In priority order. The first three are bugs or usability problems found by this study. The rest target the measured
performance gaps.

| # | Change | Why (evidence) | Size |
|---|---|---|---|
| 1 | Map an unknown enum constant to `JsonTypeException`, and list the allowed values. For example, generate a call to a library helper instead of a bare `enumValueOf`. | `IllegalArgumentException` escapes `JsonException` handlers and Ktor's `JsonConvertException` wrapping ([kson-checks.md](benchmarks/results/kson-checks.md)). | small |
| 2 | Generate each `@Kson` type's codec once and have other roots call it, instead of copying nested models into every root. | The same user decoded through two roots is not `==`; the model bytecode is 2.4× Moshi's. | medium |
| 3 | Put a JSON path in decode errors (`$.users[412].address.geo.lat`), and leave out the payload excerpt or make it opt-in. | Nested errors can't be located, and response data ends up in logs ([Error messages](#error-messages)). | medium |
| 4 | Make `JsonNumber` cheap: compute the canonical form only for `equals`/`hashCode`, replace `by lazy` with a plain cached field, and add a fast path in `toLongOrNull` for plain integer literals. | About 7 objects per number (JOL), and a `StringBuilder` on every `.long` read. Helps the tree API and the typed path alike. | small |
| 5 | Have the generated encoder write straight to a `StringBuilder` (for example, an `encodeToString(value)` next to the existing `encode(): JsonObject`). | Encoding is 2.6× slower than kotlinx.serialization and allocates 4.5× as much, mostly for the intermediate tree. | medium |
| 6 | Have the generated decoder build the `Impl` directly from locals, and use the builder only to resolve defaults. | Removes one delegate and one box per property per object. | medium |
| 7 | Add a streaming decode that reads tokens from a `String` or `ByteArray` without building a tree, and let the Ktor/Retrofit converters feed it bytes. | 70% of decode allocation is the intermediate tree. Without it, kson's allocation should approach Moshi's and kotlinx.serialization's, but that is untested. | large |
| 8 | Close the feature gaps that are most likely to block adoption: `Map<String, T>` (with a correct error message until then), a `@KsonName` key annotation, pluggable adapters for types like `Instant`/`BigDecimal`, recursive models, and a `copy`-style update. | [Supported types](#supported-types). | varies |

After each change, re-run `./gradlew -p docs/benchmarks jmh behavior ksonChecks` and update this document.

## When to choose which

- **kson** fits when you want a single dependency-free library that combines typed responses, an untyped JSON value
  API with exact numbers, jq queries, and JSON Schema. It also fits when you want interface models with builder DSLs
  and strict type checking. Its decode speed is competitive today. Before relying on it, check whether you need `Map`,
  polymorphism, custom types, or recursion, and treat items 1 and 2 above as known issues.
- **kotlinx.serialization** was the fastest encoder and decoder in this run and supports every Kotlin platform. It
  has the widest feature set among the Kotlin-first options. Its strict defaults (unknown keys are errors) usually
  need `ignoreUnknownKeys = true` for third-party APIs.
- **Moshi** allocated the least per decode, is safe with Kotlin nullability, and is JVM/Android only.
- **Gson** is fast and small but ignores Kotlin nullability and defaults, which led to `null` in non-null properties
  in seven of the cases here. It is best avoided in new Kotlin code.
- **Jackson** covers the most features but adds a 5.6 MB runtime and a 240 ms cold start, which rules it out for
  most Android apps.

## Limits of this draft

- **One machine, HotSpot only.** An Android device (ART, with a different JIT and GC) will show different absolute
  numbers and possibly different gaps. Kotlin/Native, where kson and kotlinx.serialization are the only options,
  was not measured.
- **Default configurations.** Tuned setups, such as Jackson with Afterburner/Blackbird or a reused `Json` with
  `ignoreUnknownKeys`, were not measured.
- **Jar sizes are before R8.** App size after shrinking would be the more useful number for Android.
- **One payload shape.** Payloads that are mostly numbers, or mostly long strings, will shift the ratios.
- **Rows marked *(docs)*** come from each library's documentation and were not re-verified here.

## Reproduce

Everything runs from the repository root with the checked-in Gradle wrapper. The benchmark build pulls kson and
kson-ksp from this checkout through `includeBuild("../..")`, so it always measures the current source.

```bash
./gradlew -p docs/benchmarks behavior      # results/behavior.md        (about 30 s)
./gradlew -p docs/benchmarks ksonChecks    # results/kson-checks.md
./gradlew -p docs/benchmarks retained      # results/retained.md        (JOL)
./gradlew -p docs/benchmarks footprint     # results/footprint.md
docs/benchmarks/scripts/kson-type-probe.sh # results/kson-type-probe.md (about 3 min)
./gradlew -p docs/benchmarks jmh           # results/jmh-human.txt, jmh-raw.json (about 12 min)
./gradlew -p docs/benchmarks jmh -Pjmh.includes='DecodePage'   # a subset
```
